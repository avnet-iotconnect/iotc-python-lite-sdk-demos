Concepts · 1 of 5

What is an LLM, in hardware terms

  • A next-token predictor: text in → probability of the next token out, looped
  • A token ≈ 4 characters; every generated token reads essentially all the weights once
  • The weights are a big constant array: Danube-500M at 8-bit ≈ 496 MB; Qwen2.5-7B ≈ 15 GB at FP16
  • So generation speed is memory-bandwidth-bound — a very familiar problem
  • Parameter count buys capability; it also costs bandwidth, RAM, and storage
Meet this audience in buses and footprints: "500M parameters" = "a 496 MB structure you stream through per token" (MODELS.md). That's why tok/s — not FLOPs — is the number everyone quotes, and why this hour is about fitting the best model into the bandwidth you have.

Concepts · 2 of 5

Quantization: the first lever you pull

  • Shrink weights FP16 → INT8 → INT4: smaller, faster, usually fine
  • On this board: Danube-500M q8 = 496 MB, q4 = 345 MB — and q4 is faster everywhere
  • The catch: naive uniform 4-bit broke RAG on Danube — canned refusals instead of quoting docs
  • GGUF Q4_K_M keeps damage-sensitive layers at 6-bit — Qwen-1.5B kept its reasoning

4-bit is survivable with mixed precision, brutal without it. Quantize — then re-validate.

Real cautionary tale from MODELS.md: Danube-q4 chats fluently but scores F on RAG synthesis — quantization broke exactly the fragile skill. Analogy: precision loss in a control loop — fine until it isn't, and you find out in validation, not in the datasheet.

Concepts · 3 of 5

VLM: a camera the board can talk about

  • Vision-language model = vision encoder + LLM decoder
  • On this board: SmolVLM2-256M, INT8, ~250 MB — answers questions about a live USB-camera frame
  • Measured: vision encode ~4.4 s · first token ~4.9 s · decode ~9.5 tok/s
  • The image never leaves the board
  • Two costs to watch: the encode (per image) and the decode (per token)
ask-vlm grabs a fresh GStreamer frame and defaults to "Describe what you see" (numbers: MODELS.md VLM table — README §7 carries older figures). Privacy — inference where the sensor is — is a real product argument here. Warm-worker trick: first question pays ~40 s model load, then a resident worker answers in ~5 s (vlm_worker.py).

Concepts · 4 of 5

Agents: stop the model from guessing

  • Ask a small LLM "what time is it?" — it will confidently invent one
  • An agent fixes that: the LLM only chooses a tool → the board executes it → the answer is grounded in real output
  • This board's tools: time, SoC temperature, memory, disk, uptime, IP, USB — plus cloud tools (its own /IOTCONNECT fleet) via an on-board MCP server
request→ LLM picks tool→ board runs it→ grounded answer→ telemetry: agent_tool · agent_tool_result · agent_response
The hallucination A/B is the demo's smartest beat (demo-flow.md): ask-llm invents a time, ask-agent gets it right with the tool chain in telemetry. Be honest about small-model agents: a keyword fallback rescues unparseable tool picks (agent_router: llm/keyword) and a grounding check replaces divergent answers with the raw tool result (app.py). That's what production agents on 500M models look like.

Concepts · 5 of 5 — part a

RAG: teach the board its own manual

  • Small models hallucinate facts; RAG retrieves real passages and injects them into the prompt
  • Ingredients: an embedding model (MiniLM — 22M params, 384-dim, 88 MB) + a chunked knowledge base + similarity search
  • This board's knowledge base is literally 24 hand-written passages in a JSON file — about itself
  • RAG on: "How do I expand the root filesystem?" → the actual parted/resize2fs commands, verbatim

Grounding beats parameters — tiny Danube + RAG outscores every bigger ungrounded model on documentation questions.

Show rag-db/FRDM95_hand_made_chunks.json — a RAG DB demystified to "a JSON file of facts" is a genuine aha. Swap in your service manual and every field unit answers from it, offline. QoR (MODELS.md): Danube-q8 grades D on ungrounded general facts but A- on RAG synthesis with RAG on (overall C → B+ grounded). Embedding runs on-board at ~30 chunks/s. Keep the stale-chunk observation for the file-update slide.

The stage · board

Board

8 GB LPDDR4X · 32 GB eMMC · Wi-Fi 6 / BT 5.4 (IW612)

Pipeline

eIQ GenAI Flow — NXP's stack tying wake word, STT, RAG, LLM, and TTS together

  • What the full GenAI kit costs (measured): GenAI Flow 1.6 GB · Python AI stack 1.6 GB · llama.cpp + Qwen models 2.0 GB · SmolVLM 0.7 GB → ~16 GB still free
  • RAM at full demo state (voice session + warm agent): ≈ 5.3–6.8 GB of 8 GB
Budgets from MODELS.md "what fits" tables — engineers love a resource budget. Honest caveat: the Neutron path is experimental — B0 silicon, a device-tree overlay reserving a 4 GB CMA pool, and a ~2 min model recompile per launch. That's why the demo default backend is CPU.

The stage · accelerator

Kinara Ara-2 / NXP Ara240

  • Discrete edge NPU: ~40 eTOPS, M.2 M-key card on PCIe — purpose-built for generative AI
  • Software: eIQ AAF Connector — an OpenAI-compatible REST server (/v1/chat/completions) on the board
  • So ask-llm doesn't change — set-backend ara2 just reroutes it
  • Models stay resident on the module: zero load per prompt; during 7B generation, ~12% host CPU and host RAM flat
  • Pre-compiled models are public (Apache-2.0): Qwen2.5-7B-Instruct and Qwen2.5-Coder-1.5B on Hugging Face
Specs/stack: MODELS.md Ara240 section. Teaching point: the industry-standard LLM API, served by an M.2 card on PCIe. Runtime + connector are NXP-account-gated (not NDA); compiling custom models needs the full Ara SDK on x86_64 plus a compile license. Numbers come on the "trade-off breaks" slide — this one is what it is, that one is what it's worth.

The stage · management plane

/IOTCONNECT

  • Every board here is a normal /IOTCONNECT device — nothing workshop-specific
  • The device template is the contract: this one defines 54 telemetry attributes and 17 commands
  • D2C: ~50 attributes every 10 s over MQTT — perf metrics, AI responses, health
  • C2D: every dashboard button is a real cloud-to-device command, with an acknowledgement
  • Plus x.509 identity · OTA delivery · AI model management · file storage · fleet queries — all on a public REST API
  • Isolation is enforced by the platform, not the workshop UI: you only ever see your own board

Measuring GenAI

How performance is measured

MetricWhat it isWhy you care
LoadModel/pipeline init, before the first tokenCold-start latency; hidden in most datasheets
TTFTPrompt → first token (after load)Perceived responsiveness
tok/sCompletion tokens ÷ generation timeSustained throughput — the headline number
WallEnd-to-end, cold, as a user feels itThe honest number
CPU % · peak RAMSampled at 1 Hz during the runWhat's left for the rest of your product
  • Report load separately — never buried in tok/s
  • Know your tokenizer: some paths count real tokens, others estimate ~4 chars/token
  • The official benchmark's JSON report is the authoritative source (run-benchmark)
Definitions/methodology from BENCHMARKS.md + MODELS.md: measured via the demo's real code paths, /proc sampled at 1 Hz, load always its own column. Estimated-vs-exact tokens matters when comparing engines — GenAI Flow counts real tokens; llama.cpp and Ara paths estimate. This rigor is the difference between benchmarketing and measurement.

Measuring GenAI

Add the Ara240: the trade-off breaks

  • Same 1.5B-class model: 5.7 tok/s on the CPU → 18.7 tok/s on the Ara240 (~3.3×)
  • Qwen2.5-7B — five times the parameters — runs at 5.1 tok/s: the speed the CPU managed on a 1.5B
  • Load per prompt: zero — models stay resident on the module
  • Host CPU during 7B generation: ~12% — the A55s are free for your actual product

"Five times the parameters at the same speed. Same board — we just added the card."

MODELS.md Ara240 tables. Be honest with the gauge: 5.1 tok/s is not a big number — the win is quality-at-speed, not raw speed (the demo's video script forbids rescaling the tok/s gauge to flatter it). Quality exhibit if asked: on "What color is an apple?", only the 7B covers red/green/yellow + ripeness; the 0.5B invents black apples; the 1.5B leads with "green" (BENCHMARKS.md verbatim).

The model lifecycle · retraining

Retraining in the cloud — the loop closes

capture on device→ /IOTCONNECT file support→ S3→ SageMaker training→ conversion pipeline→ deploy to fleet (OTA / Model Push)
  • Shipping example in this repo — KWS Training Studio (Microchip SAMA7D65):
  • Capture voice-command clips on the board → dataset to S3 through /IOTCONNECT
  • SageMaker trains a PyTorch keyword model; Step Functions converts it to a board-ready TFLite package
  • The new model deploys back to the device runtime (via OTA / file-download)
  • The Create Model dialog's "Convert through sagemaker?" option is the hook into the conversion half of this machinery
Source: microchip-sama7d65-curiosity/kws-training — a complete, working retrain loop on the same /IOTCONNECT primitives attendees used today. Be precise on two points: today's Qwen LLMs are deployed, not retrained — the retrain loop is shown on a keyword-spotting model, where edge retraining genuinely pays, and the KWS example closes its loop via OTA/file-download (Model Push is the equivalent lane shown live on the previous slide). And on ownership: file upload, S3 storage, and model delivery are platform features; the SageMaker training job runs in the customer's AWS account (the board needs AWS credentials to submit it) — the platform's provisioned conv-* Step Functions pipeline is conversion, not raw training.

The model lifecycle · data

Ground truth: what your fleet knows that you don't

  • Ground truth = real field data with verified labels — the raw material of every retrain
  • /IOTCONNECT file support gives each device an S3-backed bucket: captures upload from the device and land under Telemetry Files
  • Working example — the file-upload demo (NXP FRDM-IMX93):
  • capture-picture → JPEG · record-start/stop → 30 s MP4 clips (zip-wrapped) → uploaded to S3
  • Telemetry carries the metadata: recording · pending_uploads · uploaded_clips · upload_failures · last_clip

Media + telemetry context = the raw material of a labeled dataset — add labels and it becomes ground truth.

Source: nxp-frdm-imx-93/file-upload-demo. Connect backwards: the SageMaker loop starts from exactly this kind of captured, contextualized data — and the labeling step matters: the file-upload demo's telemetry is upload bookkeeping, while the KWS demo captures clips into per-command label folders, which is what makes them ground truth. Today's demo used the same S3 path for something small: rag-show publishes RAG chunk files to Telemetry Files. Metadata is what makes media usable — a clip with device state and timestamps is a dataset row; a bare clip is just a file.

The model lifecycle · video

Live video: KVS, and what the cloud adds

  • For streams, not clips: AWS Kinesis Video Streams, provisioned per device by /IOTCONNECT at creation
  • KVS PutMedia — ingest to the cloud: durable, recorded, replayable
  • KVS WebRTC — peer-to-peer live view: sub-second latency, the board is the WebRTC master
  • Start/stop from the device's Video Streaming tab; view live in the console
  • Once media is in S3/KVS, cloud analysis is a service call away — e.g. Amazon Rekognition for labels, faces, objects → results feed telemetry, alerts, and the retraining loop
Sources: tria-vision-ai-kit-6490 kvs-webrtc + kvs-putmedia (same demos for STM32MP257). Stream resource (PutMedia vs WebRTC) is chosen at device creation with the plitekvs template. Be accurate about today's board: the workshop dashboard camera is a local MJPEG server, not KVS — KVS is the productization path for off-LAN/recorded video (genai README §12 points there). Rekognition: the demos ship the capture-and-stream half; wiring Rekognition onto S3/KVS media is standard AWS integration — the architecture, not a button in this repo.
